# 行為規格格式（Spec Format）

`docs/specs/*.md` 記錄系統**當前承諾的外部可觀測行為**。規格不是設計草稿，也不是隨時間追加的變更日誌（Changelog）；當系統行為演進時，原地更新對應規格，使其始終代表當下唯一真相。

---

## 必備章節結構

每份行為規格文檔按以下固定章節組織：

### 1. 範圍與入口（Scope & Entrypoints）

- 一句話說明本模組/特性解決什麼問題、邊界在哪裡（明確做什麼、不做什麼）。
- 列出所有外部可調用入口：CLI 子命令與參數、LocalAPI HTTP 端點、配置文件路徑、環境變量或前端路由入口。
- 引用相關的 `CONTEXT.md` 術語與 `docs/adr/` 決策文件。

### 2. 行為契約（Behavioral Contract）

- 按用戶旅程或功能子域分節描述**正常路徑下**的可觀測輸入、狀態轉換與輸出。
- 使用精確的條件句（「當輸入 X 時，系統執行 Y 並產出 Z」）。
- 規定數據結構或協議時，給出精確的字段語義與不變式（Invariants），而非拷貝大段實現源碼。

### 3. 邊界與失敗（Edge Cases & Failure Modes）

- 顯式規定異常與退化場景下的行為：
  - 網路超時、上游返回非 200、離線緩存回退（如 ETag 304 或拉取失敗保留舊配置）。
  - 非法輸入或配置校驗失敗（如 `sing-box` 語法/構建校驗未通過時絕不覆蓋已知良好配置）。
  - 權限不足（如非特權用戶開啟 `tun` 時的清晰報錯與引導）。
  - 敏感信息保護（如日志與診斷包脫敏不變式）。

### 4. 驗收條件（Acceptance Criteria）

- 以編號列表（`AC-1`, `AC-2`, ...）列出可獨立驗證的斷言。
- 每條驗收條件必須滿足**可證偽性**：能夠直接映射為一個單元測試、集成測試或黑盒命令驗證。
- 任務切片（`docs/tasks/*.md`）直接通過 `AC-*` 編號引用本章節。

### 5. 已知限制（Known Limitations）

- 誠實記錄當前階段有意延後或受平台限制暫不支持的邊界（例如某里程碑暫未開啟某平台特性），並標註計劃解決的里程碑或關聯任務。

## 內容歸屬檢查表

動筆寫規格前，用下表確認內容沒有放錯地方：

| 內容類型 | 正確去處 | 禁止寫入 `docs/specs/` 的原因 |
| --- | --- | --- |
| 領域名詞定義（什麼是「配置派生」「三層狀態」） | `CONTEXT.md` | 避免多處定義導致詞義漂移 |
| 產品定位、目標用戶、里程碑範圍 | `PRODUCT.md` | 規格聚焦具體系統行為，不重複產品願景 |
| 為什麼選 `sing-box` 庫而非外部二進制、為什麼用根目錄 Go 包 | `docs/adr/NNN-*.md` | 規格只寫「現在怎麼工作」，歷史權衡與被拒方案歸 ADR |
| 顏色、字體、間距、動效曲線、卡片視覺規範 | `DESIGN.md` | 視覺設計語言獨立維護 |
| 分哪幾個切片實施、當前進度、測試輸出日誌 | `docs/tasks/<slug>.md` | 規格是長期契約，不混入臨時施工腳手架 |

## 修訂檢查（Revision Checklist）

每次新增或修改 `docs/specs/*.md` 後自檢：

- [ ] 是否使用了 `CONTEXT.md` 中的標準術語？
- [ ] 是否只描述外部可觀測行為，沒有洩漏隨時可能重構的私有函數名或源碼行號？
- [ ] 每個正常行為是否有對應的失敗/邊界處理定義？
- [ ] 每條 `AC-*` 是否具體到可以直接寫出斷言（Assertion）？
- [ ] 是否使用繁體中文且遵守單行段落（`proseWrap: "never"`）格式要求？
