# 行為規格格式

行為規格記錄可長期依賴的對外承諾。Code-first 的工作入口見 [開發管線](dev-pipeline.md)：不要求每項修改先產生 spec。小功能的驗收可以直接放 [任務記錄](../tasks/README.md)。

本目錄的 `dev-pipeline.md`、`spec-format.md` 是工程流程與格式參考，毋須套用下列產品行為章節。

## 甚麼時候需要規格

只有行為跨任務或跨消費者、存在兼容承諾、失敗語義容易誤解，或需要長期回查時，才建立 `docs/specs/<area>.md`。高風險的接口、不變式及恢復方案在改動前寫清；探索性細節隨第一條實際切片核實，於同一交付整理。

規格是承諾，來源與測試證明實作。發現不符時先判斷缺陷、未實作要求或過期契約；不以目前 bug 自動修改承諾。更新後原地描述當前有效契約，歷史權衡交 ADR，進度交任務。

## 內容結構

按適用程度精簡，但每個承諾都須有正常、失敗及可驗收的描述。

### 範圍與入口

說明解決甚麼問題、明確邊界及所有受本契約影響的外部入口，例如 CLI、LocalAPI、配置、平台接口或前端操作。引用真實存在的相關詞彙與決策。

### 行為契約

以輸入／前提、操作、狀態轉換與可觀測輸出描述行為。接口包含欄位語義、不變式、兼容及資料來源；不要抄私有函數或綁死易變行號。

### 邊界與失敗

寫清超時、斷線、非法配置、權限不足、舊資料及能力不支援等相關情境。說明錯誤回報、已知良好狀態是否保留、是否重試及如何恢復。敏感資料保護按實際入口描述。

### 驗收條件

使用 `AC-1`、`AC-2` 等編號；每條能映射為測試或實際運行斷言。列出具體輸入及結果，避免「正確運行」這類不可證偽說法。任務引用完整規格路徑及編號。

### 已知限制

分清已承諾但未實作、已實作但未驗證及刻意不支援的範圍。需要後續工作時指向實際任務；沒有任務時直接陳述限制，不虛構里程碑。

## 修訂完成條件

- 使用詞彙表中的同一名稱。
- 承諾可從外部觀察，相關失敗與恢復語義清楚。
- AC 能指向實際測試／命令；沒有執行的驗收未被寫成通過。
- 受影響程式碼、消費者與文件已核對，兼容影響有交代。
- 路徑、連結、命令及文件狀態已核實；繁體中文、單行段落與 Oxfmt 檢查通過。
