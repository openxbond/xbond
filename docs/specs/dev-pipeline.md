# Code-first 開發管線

本文件是工程工作流，配套 [ADR-001](../adr/001-dev-pipeline.md)。它是 `docs/specs/` 中的流程文件，不套用產品行為規格的 AC 模板。

## 理念與事實來源

**先取得程式碼與可運行行為的證據，以最小可用切片推進；文件只保存後續確實會讀取的意圖、契約、決策及未完工作。**

Code-first 不限定先寫實作還是先寫測試；已知 bug 先取得失敗證據，功能先交付穿過真實邊界的窄路徑。原型用於消除不確定性，不能以假資料或硬編碼成功代替生產能力。使用者已授權的任務可持續實作，無須再為例行編輯逐步請示；產品方向未明、不可逆操作及未獲授權的外部動作才需要相應決定。

| 需要知道甚麼                     | 唯一落點                              |
| -------------------------------- | ------------------------------------- |
| 當前如何實作、哪些行為可重現     | 原始碼、測試及實際運行結果            |
| 產品想解決甚麼、已確認設計要求   | `PRODUCT.md`、`DESIGN.md`             |
| 名詞代表甚麼                     | `GLOSSARY.md`                         |
| 對外承諾與兼容邊界               | 有需要才建立的 `docs/specs/<area>.md` |
| 為甚麼作這個架構選擇             | `docs/adr/NNN-<slug>.md`              |
| 未完工作、驗收、依賴、證據與接續 | `docs/tasks/<slug>.md`                |
| 已合流／已發佈版本               | 實際提交、PR、tag 與產物摘要          |

程式碼不自動成為產品意圖；設計要求也不自動成為已交付功能。發現差異時，先分類為缺陷、未完需求或過期文件，再修復正確的一方。

## 入口路由

| 工作入口 | 第一個可審查產物 | 文件要求 | 完成界線 |
| --- | --- | --- | --- |
| 小修、文案、格式、單點低風險調整 | 最小 diff | 交付摘要即可 | 最窄檢查通過，影響說明清楚 |
| 可重現缺陷 | 失敗測試、重現命令或截圖 | 複雜／跨會話才記任務 | 修復後原重現不再失敗，相關回歸通過 |
| 新功能或跨模組改動 | 一條端到端可運行切片 | 任務內寫目標與可證偽驗收 | 驗收逐項有程式碼及運行證據 |
| 需求或接口不確定 | 有界研究或可丟棄原型 | 記錄要回答的問題、時限與結論 | 不確定性已解決，或清楚指出需使用者決定的缺口 |
| UI 變更 | 既有畫面證據與實際介面 diff | 讀產品、設計及 UI 分支；跨會話記任務 | 行為驗證與有界視覺驗證完成 |
| 行為保持的重構 | 既有行為基線與第一個小 diff | 改邊界才記決策 | 對外行為不變、相關測試通過 |
| 審查 | 相對固定基準的 diff 與發現 | 記錄基準及 Standards／Behavior 兩軸 | 重要發現修復或交由有權者明確接受 |
| 發佈／回退 | 指定提交的已驗證產物與恢復方案 | 記錄平台、版本、摘要及授權 | 指定產物已發佈且冒煙驗證通過；本機封裝不等於發佈 |

## 開工：核對意圖與工作樹

1. 讀根 `AGENTS.md`、任務涉及的領域文件及現有任務；確認目標、非目標與可證偽的完成條件。
2. 查看工作樹，辨認既有改動。結構探索按 codebase-memory 的圖、覆蓋檢查及來源回退規則進行；文字、設定與文件直接搜尋。
3. 選入口與驗證範圍。已有測試就先跑相關基線；舊失敗需記錄及區分，不擴大任務去修無關問題。
4. 對有風險的跨邊界變更，先寫足以指出接口、不變式、影響與恢復方式的短決策；存在未解的產品選擇才請使用者定奪。

**完成條件：** 目標、受影響入口、驗收方式及已知基線清楚；可以開始第一個可回退切片。小修可在回覆中說明，不要求先寫文件或等待 plan 審批。

## Build／Test：最小端到端切片

1. 從真實入口穿過必要邊界，交付一條可運行窄路徑；例如 LocalAPI 操作連到實際核心結果，或 UI 操作收到真實接口回應。先縮小範圍，不先建立全套抽象。
2. 缺陷以原失敗場景驗證；新增行為以外部可觀測的成功、失敗及恢復斷言驗證。替身可隔離網絡與權限，必須標明它證明不到的邊界。
3. 每個切片做相關最窄檢查，通過再擴展；新失敗或新增影響才擴大重跑。[驗證矩陣](../agents/verification.md) 定義語言、宿主及平台的證據。
4. 更動 LocalAPI、狀態欄位、訂閱格式或核心配置時，同時核對受影響的生產者、消費者、持久化與舊資料；失敗不得覆蓋已知良好狀態或偽裝成功。
5. 只有高風險不變式而測試是否能攔截破壞仍存疑時，才在隔離環境作單點錯誤注入。先確認可還原、不影響真實網絡，證明檢查會失敗，再還原並通過；不是每項任務必做的儀式。
6. 實作改變了長期契約、名詞或架構決策，於同一交付更新相關文件；施工細節與命令輸出留在任務，不寫進長期規格。

**完成條件：** 本切片的驗收有實作及證據，必要文件同步，破壞性探針已還原，下一切片不依賴假成功。可獨立審查的小 diff 優先於多層空殼。

## UI 分支

共享 Web／桌面介面採 **Operate** 模式，保留 [DESIGN.md](../../DESIGN.md) 中已確認的世界與產品事實。

1. 使用已安裝的 Impeccable：在專案根執行其 launcher 的 `context` 一次；由技能提供的實際路徑定位，不硬編碼開發者家目錄。讀對應命令 reference，並在 UI 編輯前讀 craft floor。無法載入時照技能要求報告，直接讀現有上下文繼續。
2. 檢查目標程式碼與目前畫面。不能運行時，使用並核對現有截圖／golden 的來源與新鮮度；證據不足就記錄限制，不把舊圖當作新驗收。
3. 選最窄的工作：新增／替換視覺世界按 new-work；既有介面改善按對應 refine／audit 分支；不因 Code-first 略過技能明定的設計選擇或使用者確認。
4. 完整實作後，第一輪批次檢查桌面及手機寬度、明暗主題、鍵盤焦點、減少動態效果、長文案，以及本次相關的載入／空／錯誤／成功狀態。載入真實能力限制；不能只檢查預設成功畫面。
5. 問題一次修正，最多再確認一輪；Web 完成後按技能執行一次機械 detector。預算上限涵蓋截圖、掃描、微調及重建。記錄未解缺陷；超出兩輪的視覺完善另立後續工作，關鍵驗收未過不能宣告完成。
6. 截圖附平台、尺寸、主題、資料來源與情境。Mock 控制器只證明相應 UI 行為；本機代理、TUN、原生 VPN 與端到端連通仍須各自驗證。

**完成條件：** 本次 UI 驗收有實際操作與畫面證據，已確認設計未被意外替換，狀態來源與平台限制交代清楚。純流程文件工作不要求製造 UI 變更或截圖。

## Review：固定基準、兩軸核對

審查前固定比較基準（提交、merge-base 或本次檔案清單）；把原有未提交改動與本次範圍區分。若使用的 code-review skill 有獨立代理要求，依其規則執行；一般工作不為湊角色開多代理。

| 軸 | 核對內容 | 可接受證據 |
| --- | --- | --- |
| Standards | 本倉庫規則、模組邊界、錯誤處理、敏感資料及目標平台兼容 | 具體 diff、相關來源與必要靜態檢查 |
| Behavior | 使用者目標、任務驗收、既有契約、失敗／恢復及行為回歸 | 測試、重現命令、操作結果及對應畫面 |

技能若稱第二軸為 Spec，映射為此處的 Behavior：已有 spec 時核對 spec；沒有時核對使用者目標、任務驗收與現有行為測試，不能以「缺 spec」阻止小修。

每個發現附可觸發情境、實際影響及精確位置；格式器已處理的格式問題不重複報告。修復後只重跑受影響檢查。自查如實標記自查，不宣稱獨立審查或真人批准。

**完成條件：** 阻塞正確性、資料安全或驗收的發現均已修復，或由有權者明確接受並記錄；檢查證據與當前 diff 相符。沒有分支保護或 CI 的證據，不宣稱已合流或門禁已自動執行。

## Release：本機產物到明確授權的發佈

1. 確認本次授權涵蓋的目標、版本及平台。一般實作可完成本機檢查、建置、封裝及待審產物，不自動延伸為公開發佈。
2. 以指定提交建立產物，記錄工作樹是否乾淨、工具鏈、驗證與摘要。未提交改動產物標明開發用途，不冠以可重現正式版本。
3. Web 產物使用 `pnpm build`、`pnpm release:package dist release-assets/<version>`、`pnpm release:validate release-assets/<version>/dashboard.zip release-assets/<version>/SHA256SUMS`。目錄中的版本須換成實際版本。
4. 桌面使用目標宿主建置／簽署／安裝冒煙；移動端須相應 SDK、簽署與裝置驗收。Web zip、Go 測試及 Rust 編譯均不能代替這些結果。
5. `pnpm release:transfer <tag> <directory>` 會寫公開產物倉庫並觸發下游；只在明確授權後執行。先讀當前腳本確認 tag、目標及內容；不覆蓋已發佈版本。
6. 發佈前指明上一個已驗證產物及其恢復／安裝步驟，涉及持久化變更時交代兼容和恢復。發佈後驗證啟動、關鍵操作及版本；失敗回到缺陷入口，回退同樣遵守授權。

**完成條件：** 能指到實際 tag／提交、平台產物及驗證結果，恢復方案可執行。只做本機準備時，交付明確標為待發佈。

## Maintain：把失敗帶回程式碼

使用者報錯、運行失敗或已存在的監測告警，記錄版本、平台、可脫敏的重現資料、預期與實際結果；先判斷是否重複問題，再回到缺陷或研究入口。確定根因後保留能攔截同類問題的行為測試；重複的 Agent 失誤才補一條精確規則，能由程式檢查的規則優先自動化。

未配置的監控、排程、hooks、GitHub Actions 或自動回退屬後續工程，不因寫入流程就視為已啟用。不默認採集使用者流量或診斷資料。

**完成條件：** 問題有處理決定；修復有回歸證據，延後有可追蹤任務，拒絕有理由。重複問題連回原記錄，避免創建無限任務。

## 交付與接續

功能或跨會話任務按 [任務記錄](../tasks/README.md) 更新；短任務以同樣資訊在交付摘要記錄：

- 實際改了甚麼及原因；本次 diff 範圍。
- 驗收對應的測試／命令、結果與執行環境。
- 自查／審查結果，未執行的驗證及其限制。
- 當前交付階段：本機完成、待平台驗證、待合流或已授權發佈。
- 尚未完成時的下一個具體操作、阻塞原因及相關路徑。

不以文件齊全、測試數量或程式碼行數判定成功。回顧時按需要看從請求到第一條運行切片的時間、審查等待、返工及交付後回歸，資料不足就不編造基線。
