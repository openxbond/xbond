# ADR-001：Code-first 開發管線

- **狀態**：已採納（Accepted）
- **日期**：2026-10-27；2026-10-28 補全決策內容
- **關聯領域**：`AGENTS.md`、工程 skills、`docs/agents/`、`docs/specs/`、`docs/tasks/`

## 背景與問題

XBond 客戶端有 Go 本機服務、React 共用介面、Tauri 殼及原生平台接入。跨端同名能力不代表都已實作或驗證；只有文件、mock 或某一層綠燈不足以證明實際交付。

倉庫已選本地任務記錄、五個預設分診角色與單上下文領域文件。原任務模板預設獨立規格及探針，並引用不存在的模組或路線圖；需要改成按真實任務風險與證據推進的流程。

使用者明確選擇 Code-first。參考 [The AI-native SDLC playbook](https://claude.com/resources/articles/the-ai-native-sdlc-playbook) 的短回饋、持久上下文及風險治理，按本倉庫規模調整產物與關卡。

## 考慮過的方案

### 每項工作先經 intent、spec、plan 再實作

優點是前置工件一致，適合有明確監管或跨團隊交接需求的環境。代價是小修也需維護多份重複意圖，真實實作證據較晚出現。

### 只寫程式碼，意圖與證據留在會話

短任務開銷低，但跨會話會丟失驗收、平台限制與未完工作，也難以判斷現有行為是刻意契約還是缺陷。

### Code-first，按需要保存上下文

先從既有程式碼與重現出發，交付可運行窄切片；長期契約、架構理由及跨會話進度分別保存在單一落點。額外文件由風險、兼容或協作需要觸發。

## 決策

採第三案。具體流程以 [開發管線](../specs/dev-pipeline.md) 為準，驗證以 [驗證矩陣](../agents/verification.md) 為準。

1. 小改可直接實作與驗證，不設一律的計劃審批。新功能以真實端到端切片推進，缺陷先取得可重現失敗。
2. 程式碼、測試及運行結果證明現況；使用者要求與行為契約決定應然。兩者衝突必須查明，不把 bug 追認為規格。
3. `AGENTS.md` 保存通用規則與條件式上下文指向；skills 的預設載體映射到 `docs/agents/`。不複製第三方 skill，不建立平行事實來源。
4. 任務內可直接寫驗收；規格只保存跨任務契約，ADR 保存決策理由，任務保存進度與證據。不存在的規格或 roadmap 不作前置依賴。
5. UI 工作使用 Impeccable，保留已確認設計與有界視覺驗證。介面、宿主、流量接管及外部連通的驗收分開證明。
6. 審查覆蓋 Standards 與 Behavior；沒有獨立 spec 時以目標、任務驗收及行為測試核對。重要風險交有權者決定。
7. 本機實作與檢查沿已授權範圍自主完成；公開發佈、遠端變更及合流依實際授權執行。未安裝的 CI、hooks 或監測不視為門禁。

## 後果與取捨

- 第一個可運行結果更早出現，小改不必維護多份前置文件。
- 需要主動把已確認契約與決策在同一交付整理，否則 Code-first 會退化成只有會話記憶。
- 多語言及平台驗證仍有成本；不能以 Web 成功代替原生成功，也不能在缺少平台時宣稱完成驗收。
- 現階段品質命令由開發者／Agent 執行，遠端強制門禁尚未建立。後續自動化須先證明工具鏈與 runner 可運行，再另行接入。
